# 实时录制 + 击杀标注方案（Outplayed 式）

本文只讲设计，代码还没写。所有数字都是这台机器上刚测的，不是估的。

## 1. 要做的功能（对齐 Outplayed）

| Outplayed 的功能 | 我们这版怎么做 | 阶段 |
|---|---|---|
| 后台一直录，不占前台 | ffmpeg 子进程 + NVENC 硬编，Python 只做调度 | P0 |
| 全局录像 / 单局分割 / 手动 / 高光 四种模式 | 同一套底层，只在「起停时机」和「保留策略」上分叉 | P0 / P3 / P4 |
| 一局一局分文件夹 | **读左上角「对局编号」**，每局一个（已确认），打点带着编号归组 | P3 |
| 击杀/击倒自动打点 | 复用现有播报识别（模板找图标 + 只认昵称） | P1 |
| 打点后自动出片段 | 复用 `clipper.plan/cut_all`，按击杀前/后秒数切 | P2 |
| 游戏开了自动录、关了自动停 | 轮询 `Calabiyau-Win64-Shipping.exe` + 窗口矩形 | P3 |
| 编辑器 / 上传 / 分享 | **不做** | — |

## 2. 实测结论（决定方案的依据）

这台机器：RTX 5060 8 GB，驱动 617.42，屏幕实际 2560×1600（Windows 150% 缩放，逻辑 1707×1067），D 盘剩 77 GB。
ffmpeg 是 `D:\game\Apex Highlight Clipper\resources\tools\ffmpeg.exe`（9.0.2，带 `ddagrab` + `h264_nvenc`/`hevc_nvenc`/`av1_nvenc`）。

| 测的东西 | 结果 |
|---|---|
| 桌面采集 `ddagrab` | 可用，直接拿到 2560×1600，配 `hevc_nvenc` 正常出片 |
| 采集指定区域 | `ddagrab` 支持 `video_size` + `offset_x/offset_y`，可只录游戏窗口 |
| 分段录制 | `-f segment -segment_time 4` 默认**切不齐**（要等关键帧），必须加 `-g 60 -forced-idr 1`；切出来的段 OpenCV 能直接读（123/120/60 帧） |
| 录制 + 采样同时跑 | 两个 ffmpeg 进程各开一个 `ddagrab` **互不冲突**，录制 12 秒 + 2 fps 采样实测同时成功 |
| 采样帧到 Python 的延迟 | 首帧约 0.8 秒，之后每 0.5 秒一帧，读帧本身几乎不耗时 |
| 播报区图标检测成本 | 整帧找 680 ms（太慢）；**先裁播报区再找，97 ms**；播报区缩一半 25 ms |
| 播报区完整识别 | `feed.read_rows` 52 ms（没有命中时） |
| 画质/容量（60 fps，2560×1600，hevc_nvenc） | `-cq 26` ≈ **6.7 GB/小时**；`-cq 30` ≈ **4.4 GB/小时**；编码速度约 3× 实时 |
| 画质/容量（**120 fps**，2560×1600，hevc_nvenc） | cq24 ≈ **10.4 GB/h**、cq26 ≈ **9.3 GB/h**、cq28 ≈ **7.7 GB/h**、cq30 ≈ **6.3 GB/h**；编码速度 **1.6× 实时** |
| 多音轨 | mkv 可以放多条音轨；但**现在的 `clipper.cut` 用 `-c copy` 没有 `-map 0`，切片段时会把第二条以后的音轨丢掉**（实测：2 条音轨 → 切完剩 1 条；加 `-map 0` 后 2 条都在） |
| 系统声音 | DirectShow 只有麦克风，没有「立体声混音」；要录游戏声音得装 VB-Cable 之类虚拟声卡，或以后做 WASAPI loopback |

按 120 fps / cq26 算约 **9.3 GB/小时**，D 盘 77 GB 只能录 8 小时左右 —— 「保留最近 N 小时 + 剩 10 GB 自动清最旧」必须做。

## 3. 架构

```
ui.py (HTTP/SSE)
  └── Hub / RecorderController
        ├── recorder.py   → ffmpeg #1：ddagrab → hevc_nvenc → 分段 .mkv + seg.csv
        ├── livefeed.py   → ffmpeg #2：ddagrab@2fps → rawvideo 管道 → feed 检测 → markers.jsonl
        ├── session.py    → 会话目录、时间轴、切片（调 clipper）
        └── watcher.py    → 现有「盯录像文件夹」模式保留，两套互不干扰
```

两个 ffmpeg 各干一件事，互不阻塞：录制的挂了不影响打点（只是没画面可切），打点的挂了录制照常。

## 4. 录制

```
ffmpeg -f lavfi -i "ddagrab=0:framerate=120:draw_mouse=0:video_size=2560x1600"
       -f dshow -i audio="麦克风 (UGREEN USB MIC-CM564)"
       -f dshow -i audio="CABLE Output (VB-Audio Virtual Cable)"
       -map 0:v -map 1:a -map 2:a
       -c:v hevc_nvenc -preset p4 -cq 26 -g 240 -forced-idr 1
       -c:a aac -b:a 192k
       -metadata:s:a:0 title="麦克风"
       -metadata:s:a:1 title="游戏"
       -f segment -segment_time 10 -reset_timestamps 0
       -segment_list seg.csv -segment_list_type csv
       out/seg-%04d.mkv
```

- **分段 10 秒**：程序崩了最多丢 10 秒；每个段都是独立可读的 mkv。
- **`-reset_timestamps 0` + `seg.csv`**：每段带全局时间戳，段边界时间从 csv 里读，打点和切片都用同一条时间轴，不用猜。
- **不写 mp4**：mp4 要做 moov 收尾，进程被杀就废了；mkv 稳。
- **无边框全屏**：这是硬要求（写进使用说明）。独占全屏下 DXGI 桌面复制可能黑屏，我们不做兼容，检测到黑屏就直接提示「请把游戏改成无边框全屏」。

### 4.1 视频参数（全部界面可调，调试模式里展开）

| 参数 | 选项 | 默认 | 说明 |
|---|---|---|---|
| 分辨率 | 跟随窗口 / 1920×1080 / 2560×1600 | **跟随窗口** | 跟随窗口时用 `ddagrab` 的 `video_size`，不缩放最省性能 |
| 帧率 | 30 / 60 / 120 / 144 | **120** | 120 fps 编码约 1.6× 实时，能顶住；144 会更紧 |
| 编码器 | `hevc_nvenc` / `h264_nvenc` / `av1_nvenc` / `libx264` | **hevc_nvenc** | HEVC 同画质体积最小；兼容性差就换 h264；CPU 兜底会比游戏抢资源 |
| 码率控制 | CQ / VBR 目标码率 / CBR | **CQ** | 录制用 CQ 最省心，画面复杂时自动加码 |
| CQ 值 | 18–34 | **26** | 越低越清晰越大；24≈10.4 GB/h、26≈9.3、28≈7.7、30≈6.3（120 fps 实测） |
| 目标码率 | 10–120 Mbps | 40 | 选 VBR/CBR 时才有意义 |
| 预设 | p1（最快）–p7（最好） | **p4** | p1 更省 GPU、画质略降 |
| 关键帧间隔 | 1 / 2 / 4 / 10 秒 | **2 秒** | 越短切片越准、体积越大；120 fps 时 2 秒 = 240 帧 |
| 分段长度 | 5 / 10 / 30 秒 | **10 秒** | 只影响崩溃容错和切片粒度 |
| 色彩 | 8bit / 10bit | **8bit** | 10bit 需要 HDR 显示器且播放器要支持 |
| 录鼠标 | 开 / 关 | **关** | |
| B 帧 / lookahead | 高级 | 默认 | 放调试模式，别让用户乱动导致卡顿 |

**CQ 给多少**：网游录制用 NVENC 一般 CQ 23–28。120 fps 我们默认 **26**——比 24 省 10%，肉眼几乎看不出差别；想要更清晰就 24，硬盘吃紧就 28。

### 4.2 音频（多条音轨，每路输入一条）

- **设备可选、可多选**：界面里列出所有 DirectShow 录音设备（`ffmpeg -list_devices true -f dshow -i dummy` 解析），勾几个就录几条。
- **每路一条独立音轨**，不混在一起：
  - 游戏声音 → 一条（需要装 VB-Cable 之类的 loopback 设备，否则这个设备列表里根本没有）；
  - 麦克风 → 一条；
  - Discord / 音乐软件 → 再来一条。
  - 用 `-map 1:a -map 2:a …` 输出成 mkv 的多条音轨，并给每条写 `title`（"游戏"/"麦克风"/"Discord"），播放器里能单独选、单独静音。
- **每条音轨可单独设**：编码（aac / pcm 无损）、码率（128/192/256 kbps）、采样率（48k）、声道、增益（dB）、是否启用。
- **切片段时必须 `-map 0`**：不然除了第一条音轨全丢（已实测确认，`clipper.cut` 要改）。
- **注意**：如果某条设备中途被拔了（USB 麦克风、耳机切换），ffmpeg 会报错退出。处理办法是「哪条断了就重启录制进程，其余音轨继续」，界面上提示一次，不要静默失败。

## 5. 击杀打点

- **采样器**：第二个 ffmpeg，`ddagrab=framerate=2`，`-vf hwdownload,format=bgra`，`-f rawvideo` 到 stdout，Python 读 2560×1600 的帧（16 MB/帧，2 fps = 32 MB/s，实测无压力）。
- **检测**：先按 `geometry.region(profile, "kill_feed")` 裁出播报区，再 `feed.find_icons`（97 ms）；命中才 `feed.read_rows` 认昵称（52 ms + OCR）。2 fps 下 CPU 占用约 10–20% 一个核。
- **去重**：同一播报行会在屏幕上停好几秒，用现有 `feed.name_score(victim) >= 0.6` + 8 秒窗口去重。
- **计分板跳过**：`roster_scan.looks_like_scoreboard(..., recognizer=...)`（10–15 ms/次），或直接用已知的计分板时间点。
- **时间**：`marker.time = read_time - 0.25`（半个采样间隔），误差 ±0.5 秒；切片窗口一般 10 秒前 3 秒后，够用。以后要更准可以用 ffmpeg 的 `showinfo` 对齐 PTS。
- **落盘**：`markers.jsonl` 一行一个 `{time, kind, victim, killer_character, score}`，追加写 + flush，进程崩了也留得住。

## 6. 切片（复用现有 clipper）

一段片段可能横跨多个录制分段，做法：

1. 从 `seg.csv` 找出与 `[start, end]` 相交的段；
2. 生成 concat 列表，`ffmpeg -f concat -i list.txt -ss <相对偏移> -t <时长> -c copy` 直接切，**不重编码**；
3. 文件名沿用现有规则 `clip-003_击杀×2_102.5-118.0s.mp4`。

因为段是按关键帧切的、编码参数一致，concat + copy 切出来是干净的（这点和现在切 NVIDIA 录像一样）。

**实时出片**：击杀发生后等 15 秒（确保相关分段都已封口），后台自动切一段放进 `clips/`，界面里点开就能看。不需要等整局结束。

## 7. 一局一局怎么切：直接读左上角「对局编号」

不用猜。左上角那行 HUD 就是 `765071518099047823 C1.18.6.11 S1.18.6.12`：
前 18 位是这一局的编号，`C…` 是客户端版本，`S…` 是服务器版本。

- **现成的区域**：标定档里就有 `match_id`（1920 基准 `[28,56,320,84]`，左上锚点），现在没人用。
- **读法**：只裁前 18 位那个小块（1920 基准约 `[26,55,232,88]`），走 **rec-only**（不做检测），**13–16 ms 一次**，正则抓前导数字即可。
  - 对比：同一块走「检测+识别」要 **2184 ms**，绝对不能用。
- **采样频率**：2 秒一次，代价约 7 ms/秒，可以忽略。
- **判据**：
  - 读到编号且连续两次一致 → 这就是「当前这一局」；
  - 编号变了 → 开新局；
  - 某个采样读不到（被回放/结算画面挡住）→ 沿用上一个编号；超过 30 秒读不到才认为离开对局。
- **每个打点都带上当时的编号**，所以「一局一局」不是靠切录像文件，而是**靠归组**：
  录像本身连续录、不按局打断（避免跨局拼接），片段和击杀列表按编号归到 `matches/<编号>/` 下，文件名直接用它。
- 实测两个录像的编号：`753029202910957071`（10-11）、`765071518099047823`（10-27），确实不同。

**已确认：这个编号就是每局一个**（作者确认），所以「局」不需要再猜边界——编号变了就是下一局。

## 8. 四种录制模式

四种模式共用同一套底层（分段录制 + 打点 + 切片），区别只在两件事：**什么时候开始/停止整体录制**、**最后留下什么**。

| 模式 | 开始 | 停止 | 落盘产物 | 磁盘 |
|---|---|---|---|---|
| **全局录像** | 检测到游戏启动（或点开始） | 游戏关闭（或点停止） | 一次游戏一个会话目录，内含全部段 + 一个拼接好的完整录像 + 按编号归组的片段 | 最费：整段时间 × 9.3 GB/h（120fps cq26） |
| **单局分割** | 对局编号第一次出现即开录 | 编号消失/变化 → 停录、封口、拼成本局一个文件；下一局重新开 | 每局一个 `2026-11-01_21-33_match-765071518099047823.mkv` + 该局片段 | 只算对局时间 |
| **手动** | 热键 F9 / 点按钮 | 再按 F9 / 点停止 | 一段一个文件 | 你按多久算多久 |
| **高光** | 一直录（环形缓冲） | 不主动停；只在命中击杀时落盘 | **只有片段**，没有全程录像 | 只有片段大小 |

三个模式（全局 / 单局 / 手动）都是「先完整录，再切片」；**高光模式是「只切片」**。

### 8.1 高光模式的「缓冲」到底是什么

一句话：**一直在录，但硬盘上永远只保留最近十几秒，早的随时删；听见击杀才把需要的那几秒「抢救」下来。**

具体怎么转：

```
时间 →  90s        95s        100s        105s
        [段1][段2][段3][段4][段5][段6][段7]     ← 每 10 秒一段，边录边写
                          ↑
                    100.0s 击杀（播报出现）

保留窗口 = 前 10 + 后 3 + 余量 5 = 18 秒
  → 任何时刻，磁盘上只有 [now-18, now] 的段（默认 2 段）
  → 100.0s 时需要的是 [90.0, 103.0]
  → 等到 103.0s（后 3 秒过去、相关段都封口）再切
  → 切出 clip-001_击杀_90.0-103.0s.mp4，放进正式目录
```

几个要点：

1. **缓冲不是内存**，是磁盘上的临时段文件。用磁盘是因为 120 fps 的原始帧一秒 24 MB，放内存不现实，而且进程崩了磁盘还在。
2. **保留窗口自动算**：`前 + 后 + 5 秒余量`。你把「击杀前」调到 30 秒，窗口自动变 38 秒 —— 不需要你另外再设一个「缓冲多长」。调小了也不会缺头：窗口永远 ≥ 你设置的窗口 + 余量。
3. **为什么要等 `后` 秒才切**：击杀后的画面还没录完。等它录完、段文件封口，才能 `-c copy` 无损切。
4. **为什么要有 5 秒余量**：检测本身有延迟（采样 0.5 秒 + 识别 0.15 秒 + 写盘），余量保证切的时候起点的段还在。
5. **两次击杀挨得近**（比如 5 秒内两次）：按 `合并间隔` 规则并成一段，等最后一个击杀的窗口结束再切，不会切出两段重叠视频。
6. **删旧段的时机**：每写完一段检查一次，起始时间早于 `now - 窗口` 的段删掉。如果**删除时发现某段正被某个待切的片段需要**（击杀后那几秒），就推迟删。
7. **开销**：录制本身照常（NVENC 一直在跑），删除是文件系统操作，几乎不耗资源；真正耗时的只有命中时的 concat 切片（`-c copy`，一段几秒）。

一句话总结：**高光模式 = 全局模式 + 一个很短的滚动窗口 + 命中才另存**。所以它和全局模式共用同一套录制代码，只是清理策略不一样。

**单局分割的实现细节**：底层还是 10 秒一段地写（防崩溃），局结束时用 concat + `-c copy` 把这一局的段拼成一个文件（秒级，不重编码），再删掉中间段。

## 9. 自动启停

- 每 3 秒轮询一次 `Calabiyau-Win64-Shipping.exe` 是否存在（`Get-Process` / `toolhelp32`，不注入、不碰游戏内存）。
- 找到后用 `GetWindowRect` 拿窗口矩形：无边框全屏时矩形 = 屏幕，直接用；窗口化时用 `ddagrab` 的 `offset_x/offset_y/video_size` 只录那块，播报检测也按窗口尺寸 `geometry.for_size`。
- 游戏退出 → 全局模式封口 + 拼接 + 切片段；单局模式把当前局收尾。
- 单局模式下，编号出现 = 开录，编号消失超过 30 秒 = 本局结束（结算画面读不到编号是正常的）。

## 12. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 游戏用**独占全屏** | DXGI 桌面复制可能黑屏/失败 | 优先要求改「无边框全屏」；启动时检测一次，黑屏就提示并退回「录整个桌面」 |
| HUD 缩放和标定不符 | 播报区找不准 → 漏标 | 采集尺寸变化时自动 `for_size` 重算；首次用某分辨率时跑一次「标定检查」（裁一帧播报区给人看） |
| 双 ddagrab 抢桌面复制 | 采样或录制失败 | 已实测可并发；失败时降级为「从录好的段里补检」，只是打点慢十几秒 |
| NVENC 会话数/占用 | 游戏掉帧 | 只 1 路编码；NVENC 实测 3× 实时，占用约 1/3 编码器 |
| 硬盘被塞满 | 录制中断、系统卡 | 配额 + 满了自动删最旧 + 界面红字提醒 |
| 反作弊误判 | 封号 | 只读屏幕（Desktop Duplication）和进程列表，不注入、不改游戏内存、不 hook |
| 时钟漂移 | 点位偏 ±1 秒 | 切片窗口够大；后续用 PTS 对齐可消除 |

## 14. 还剩下的问题

已定：默认 120 fps / CQ 26、参数全部可调、音频多选多轨、硬性要求无边框全屏、热键 F9、容器 mkv、先做 P0。P0 已完成，下一步 P1（打点）。

还没定的：

1. **音频设备**：这台机器目前只有麦克风（`Microphone (UGREEN USB MIC-CM564)`），没有 loopback 设备。要录游戏声音得先装 VB-Cable 或「VoiceMeeter」之类；要我先把「检测不到 loopback → 界面提示去装」做好，还是你打算改用 WASAPI loopback（我可以直接录系统声音，不用装东西，但要另写采集路径）？
2. **保留策略**：全局模式默认「最近 10 小时 / 剩 10 GB 自动清最旧」，120 fps 下差不多 8 小时，够不够？
3. **单局文件格式**：局末拼成 `.mkv`（稳、免转码）还是转成 `.mp4`（能直接拖进剪辑软件/发群）？转 mp4 要多花一次重编码时间。

### 已知坑（P0 实际踩到的）

- **拼接时长翻倍**：分段用 `-reset_timestamps 0`，容器里每段「时长」记的是结束时刻（第 N 段显示 N×10 秒），concat 列表只写 `file` 会拼出两倍时长。必须在每段后补 `duration 结束-开始`（从 `seg.csv` 算），实测 9 秒 → 9.32 秒。
- **热键遇到管理员权限**：`RegisterHotKey` 注册的全局热键，在前台是「更高权限进程」时收不到（UIPI）。卡拉彼丘若以管理员运行，F9 会失灵 —— 提示用户用管理员身份启动本软件。
- **沙箱里测不出热键**：自动化脚本里 `SendInput` 返回 1、`GetAsyncKeyState` 恒 0、收不到 `WM_HOTKEY`，因为这个进程不在交互输入桌面上；注册结果本身可验证（`{"registered": true}`），真机由用户按键验证。
